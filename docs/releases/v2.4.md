# Obsilo Agent v2.4

**2.4.0 至 2.4.2 版本**，于 2026 年 4 月发布。

本次更新为 Obsidian 知识库引入自动化知识维护功能，增加扫描 PDF 的 OCR 支持，并提升了大文档和知识数据库的稳定性。

## 知识维护

知识库增长很快，但很少能保持有序。笔记积累却没有反向链接，frontmatter 属性偏离模式，分类变得陈旧，附件保留着相机拍摄时的原始名称。检索质量下降，因为孤立笔记在图搜索和语义搜索中都不可见。

本版本为个人知识管理添加了一层维护机制：少量强大的枢纽笔记（主题、概念）作为索引页面，通过密集的反向链接连接它们所组织的笔记。当智能体摄入新笔记时，它会首先搜索现有枢纽，仅在没有任何合适枢纽时才创建新实体。久而久之，这会形成一个可导航的、链接良好的知识图谱，每篇笔记都可以通过其主题集群到达，语义搜索也能从反向链接和 frontmatter 提供的额外上下文中受益。

### 知识摄入技能

一个内置技能，当你说"整合这篇笔记"时，引导智能体完成结构化的集成工作流程。

- **实体识别：** 智能体读取笔记并识别文中提到的主题、概念、人物、项目和组织
- **优先现有搜索：** 对于每个实体，智能体对知识库运行 `semantic_search`。现有枢纽笔记始终优先于创建新笔记——明确目标是少量强枢纽，而非大量弱枢纽
- **提议与确认：** 所有建议（属性、wikilinks、MOC 条目、存根笔记）在写入任何更改之前都会呈现给用户。未经确认不会执行任何操作
- **带内容的存根笔记：** 当发现真正的新实体时，智能体会创建一个包含简短说明、关键要点和回链到源文件的存根笔记——不是空的占位符，而是进一步思考的起点
- **来源处理：** 对于 PDF 和网页剪藏，智能体会提取作者、年份和标题，按照配置的命名约定提议文件名，并填充 frontmatter 元数据

### 知识库健康检查

一个完全在代码中运行的诊断和修复管道，无需 LLM 调用。

- **五种检查类型：** 知识图谱中的孤立边、相关笔记之间缺失的反向链接、相对于本体论的分类不匹配、指向不存在文件的无效 wikilinks，以及一般的图不一致
- **一键修复：** 模态框显示按类型分组的所有发现。点击"修复"，服务会批量修复——插入反向链接、剪除孤立边、纠正分类
- **检查点支持的撤销：** 每次修复都会先创建一个 git 检查点。如果出现问题，点击"撤销"即可恢复完全相同的前一个状态。不可能丢失数据
- **状态徽章：** 侧边栏显示带有发现数量的健康徽章。点击它可打开修复模态框

### 本体库

一个基于 SQLite 的知识库概念模式存储。

- 存储从知识图谱中提取的实体集群、关系和类型层次结构
- 支持可传递实体关联，以改进链接建议
- 供健康检查使用，根据定义的模式验证分类分配
- 在语义索引期间自动填充

### 知识维护设置

用于配置知识维护功能的专用设置部分。

- **分类属性名称：** 定义笔记类型的 frontmatter 属性（例如 `Kategorie`、`Category`）
- **摘要属性名称：** 保存简短摘要的属性（例如 `Zusammenfassung`、`Summary`）
- **来源命名约定：** 源文件名的模式（例如 `Author-Year_Title`）
- **MOC 属性：** 内容地图的可配置属性
- **所有设置均支持国际化**（德语和英语）

### 扫描 PDF 的 OCR 回退

现在通过 Obsidian 的 text-extractor 插件处理仅包含图像（无可提取文本）的扫描 PDF。

- 当 `pdfjs-dist` 从 PDF 中提取的字符少于 50 个时，解析器会回退到 text-extractor 的 OCR 缓存
- 该回退从 text-extractor 的缓存目录（`.obsidian/plugins/text-extractor/cache/`）读取——无需额外的 API 调用
- 以前不可见的扫描文档现在会出现在语义搜索结果中
- 优雅降级：如果 text-extractor 未安装或文件尚未缓存，解析器会返回有限的 pdfjs 输出并附带提示

## 大文档摄入 (v2.4.1)

现在可以附加和摄入超过 50 MB 的 PDF 和 Office 文档而不会出错。之前，一个 318 页的 PDF（64 MB）会导致 API 错误，因为完整提取的文本被嵌入到 LLM 上下文窗口中。

- **上下文截断：** 超过 80,000 个字符的文档会在页面边界处自动截断，然后再发送给 LLM。通知会告诉智能体如何读取剩余页面
- **分块读取：** `read_document` 现在支持 `start_page` 和 `end_page` 参数，允许智能体分块读取大型文档
- **附件支持：** `read_document` 和 `ingest_document` 都接受 `attachment_index` 参数，可从聊天附件读取，而不仅是知识库文件
- **大小限制：** 图片（50 MB）和文档（200 MB）有单独的限制。`ingest_document` 支持高达 500 MB 的文件，因为它写入磁盘而非上下文窗口
- **回退逻辑：** 当知识库文件解析失败（例如文件过大）时，`ingest_document` 会自动回退到预解析的附件文本

### 输入验证强化

- **数字字符串强制转换：** LLM 有时会把工具参数作为字符串传递（`"0"` 而非 `0`）。输入验证器现在会自动强制转换十进制数字字符串，仅限于简单表示法（不支持如 `"1e100"` 这样的科学计数法）
- **模式类型强制：** `attachment_index`、`start_page` 和 `end_page` 参数使用 `integer` 类型而非 `number`，以防止浮点值
- **XML 属性转义：** 附件 XML 标签中的所有文件名和路径现在都已转义，以防止通过精心构造的文件名注入

## 数据库稳定性 (v2.4.1)

知识数据库（sql.js/WASM SQLite）可能因写入期间崩溃或 iCloud 同步冲突而损坏，导致所有依赖服务（语义搜索、图谱、本体论、知识库健康）在下次启动时失败。

- **原子写入：** 数据库保存现在使用写临时文件然后重命名的模式（本机文件系统）或保存前备份（知识库适配器），防止半写入的文件损坏数据库
- **每次保存时备份：** 每次成功保存都会创建前一版本的 `.bak` 副本，提供恢复点
- **加载时完整性检查：** 数据库加载后立即运行测试查询。如果 B 树损坏，恢复会自动启动
- **自动恢复链：** 主数据库损坏？尝试备份。备份也损坏？创建一个新的空数据库并从知识库文件重建。无需手动干预
- **过期临时文件清理：** 启动时清理因中断写入而留下的孤立 `.tmp` 文件

## 聊天历史操作按钮

修复了一个错误：以前从聊天历史加载的助手消息没有操作按钮。之前只有活跃的流式聊天显示"插入光标处"、"创建笔记"、"另存为 Zettel"、"复制响应"、"重新生成"和"删除"按钮。现在这些按钮会显示在每条助手消息上，无论是来自活跃聊天还是从历史记录加载。

## OpenAI GPT-5 兼容性 (v2.4.2)

OpenAI 的更新模型（GPT-5.4 及更高版本）会拒绝已弃用的 `max_tokens` 参数并返回 400 错误。插件现在对所有直接 OpenAI API 调用使用 `max_completion_tokens`。其他提供商（Ollama、LM Studio、OpenRouter）继续使用 `max_tokens` 以保持向后兼容性。

## 社区插件合规性 (v2.4.2)

解决了 Obsidian 社区插件审核机器人的所有发现：

- **国际化：** 将知识库健康修复模态框中所有硬编码的德语字符串迁移到 i18n，添加了完整的英语和德语翻译
- **句首大写强制执行：** 移除了所有内联的 ESLint 规则抑制（禁止句子大写的规则），并重新表述受影响的字符串
- **品牌名称处理：** 将提供商品牌名称（OpenAI、OpenRouter）从 locale 模块移出到常量中，以避免句子大写误报

## 安全强化 (v2.4.2)

- **设备认证轮询：** 在 Kilo 和 GitHub Copilot 身份验证的 OAuth 设备流轮询循环中添加了最大尝试次数限制（10 分钟），防止用户放弃授权流程后无限期后台轮询
- **依赖更新：** 将 vitest 从 2.x 升级到 4.x，vite 升级到 6.4.2，解决了 CVE-2026-39365（vite 开发服务器路径遍历）和开发工具链中 3 个额外的的中等漏洞

## 其他改进

- **新聊天图标：** 从通用加号图标改为 `message-square-plus`，以获得更好的视觉区分
- **文档：** 添加了全面的设置参考、工具参考、故障排除指南，以及首次对话、入门和知识工作流程的教程
